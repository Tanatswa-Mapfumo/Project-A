# Decisions

Non-blocking implementation decisions, recorded as required by the master build
spec (working rule 15). Blocking/architectural decisions come from the spec
itself.

1. **Tests run on SQLite (aiosqlite); production uses PostgreSQL (asyncpg).**
   Tests need no external services: a template SQLite database (schema + seed)
   is copied per test for isolation. JSONB columns are stored as plain JSON on
   SQLite via a type variant. Documented deviation from "isolated test
   database" — the isolation model is per-test, the engine just differs.

2. **Initial Alembic migration creates schema from SQLAlchemy metadata.**
   `0001_initial` uses `Base.metadata.create_all`/`drop_all` so the migration
   can never drift from the models. Future schema changes get explicit
   autogenerated migrations.

3. **Mock auth mode stores PBKDF2-SHA256 hashes** (salted, 210k iterations,
   stdlib `hashlib`) in the local `auth_users` table. Raw passwords are never
   stored. Mock mode is for local dev/tests only; staging must use
   `AUTH_MODE=supabase`.

4. **Soreness convention: 1..10 for explicitly reported regions**; unreported
   regions are omitted (per section 9.10 of the spec). Pain uses the same
   scale, `null` = not reported.

5. **User-local date handling:** `profiles.timezone` (IANA name, default
   `UTC`) drives `checkin_date`, `plan_date`, streaks, and weekly windows.
   Timestamps are stored in UTC; the server-local timezone is never used.

6. **Working sets: beginner 2, intermediate 3, advanced 4** (within the spec
   ranges 2-3 / 3-4 / 3-5). `low` intensity reduces sets by 1 (min 1).

7. **Rate limiting is a per-process in-memory sliding window** on the three
   expensive routes (`POST /workouts/generate`, `GET /workouts/{id}/insight`,
   `POST /weekly/generate`). No Redis was added (spec section 30). In
   multi-replica deployments, platform or API-provider limits should be used.

8. **Equipment catalog adds a `kettlebell` category** beyond the spec's
   initial list ("Initial categories may include...").

9. **Consistency denominator:** planned sessions are inferred from the user's
   preferred training days over the last 7 local calendar days
   (`completed / planned * 100`, 0 when nothing planned).

10. **Cross-user resource access returns 404** (not 403) to avoid resource
    enumeration (spec section 25.3, Scenario G).

11. **One generated plan per check-in:** enforced by a DB unique constraint on
    `(user_id, check_in_id)`. Concurrent duplicate requests roll back and
    return the canonical existing plan (spec section 32).

12. **Quitting a session resets the plan status to `generated`** so the user
    can restart the same plan; the quit session itself is never deleted.

13. **`requires_email_confirmation`:** supported in supabase mode and
    controlled by `AUTH_REQUIRE_EMAIL_CONFIRM`.

14. **Exercise difficulty values:** `beginner` / `intermediate` / `advanced`.
    Beginners are only offered beginner-difficulty exercises; intermediate
    users get beginner+intermediate; advanced users get all.

15. **Deep Insight sections** follow the five-section shape from section 17
    for workouts and a four-section shape for weekly summaries; both are
    generated only from stored facts and persisted on first read.

16. **LLM output validation is conservative** (length cap, banned medical
    terms, no exercises outside the plan); a single-sentence check is left to
    the prompt because reliable programmatic sentence counting is brittle.

17. **`strength_progression` always reports `insufficient_data`** in the POC
    because actual working loads are not recorded yet (spec section 14.10: no
    load is invented from body weight).

18. **Workout explanation short text is duplicated** on `workout_plans.
    short_explanation` (for cheap list/home reads) and on
    `workout_explanations` (canonical, with provider/model/source facts).

19. **Fallback plan** (used after a primary plan fails validation, spec
    section 15): low intensity, up to 2 timed bodyweight mobility/core
    exercises. If even that fails, a controlled `WORKOUT_VALIDATION_FAILED`
    error is returned; invalid plans are never persisted.

20. **Pain >= 8** makes generation impossible under configured rules and
    returns `WORKOUT_GENERATION_RESTRICTED` (spec sections 14.2/14.11); pain
    >= 6 caps intensity at `low`.
